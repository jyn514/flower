i want to have better tools.

this origin of this post is two-fold:
1. i have been dissatisfied for some time now with what nix offers me. i want declarative installation for my computers, but without the nix runtime preventing me from installing things at runtime.
2. i was chatting about having a better terminal emulator; what it would be like if we could rethink the last 50 years of computer so we weren't all trying to emulate PDP-11s.

let's start with nix, since in some ways it's easier to compare to a system that already exists.
## Nix is infrastructure-as-code, and a runtime to manage that infrastructure

like many other system management tools, Nix is declarative; or, more precisely, nix is "infrastructure-as-code", since the nix language is a full-fledged functional programming language, not data. [^ansible-rant]

what does it mean to be infrastructure as code? it means there exists some interpreter or program which can ingest a plain text file as configuration and act upon your system's global state to bring it into a target state. that's an extremely broad definition, intentionally so, because i consider some things to be infrastructure-as-code that are not traditionally thought of that way:
- nix, of course. nix takes a `{shell,configuration,flake}.nix` and gives you an operating system userland or shell environment built from that file.
- terraform gives you a virtual machine (or sometimes container), usually hosted on a cloud computing service.
- docker creates a disk image of an operating system that can be run on any linux kernel.
- kubernetes and docker-compose give you a set of virtualized containers. unlike docker, they describe how the containers are *run*, not just their contents on disk.
- ansible and salt (for my purposes the differences between them are not too interesting) provision packages, files, and kernel parameters onto an existing operating system (usually via ssh)
- systemd unit files describe how to start and stop processes and daemons to bring an operating system into a "target" state.
- a dpkg or RPM file provisions a single "package" on an operating system.
- `make install` installs a single packages from source.
- a shell script that calls a package manage or otherwise installs files or packages.
- the set of shell scripts and configuration files that generate an initramfs image.

note also the things i have left out:
- "traditional" build systems, even ones with distributed compilation like bazel and buck, because they act on your local state, not global state. to the extent that they have remote execution and remote caching these are implementation details of the system; the remote environment does not *persist* after the build, and it has to be created through one of the other IAC methods here.
- github actions and other CI systems. although github actions manages (in some cases, many) machines and tasks, it does not generate a *persistent* environment for other tasks to later run in. its target state is "run this set of processes", not "change the global state of the system". [^github-deploys]

the common thread here is that IAC programs *manage their own environment* and *persist the environment after the build finishes*.
### idempotence, state management, and drift
now, when your environment is generated by code, the problem, of course, is that your environment can change after it's generated. there are roughly four ways i've seen this managed:
- "not our problem lol": shell scripts, ansible, `make install`, docker-compose[^volumes]. these mostly just give up on the problem altogether; they usually make a best-effort attempt to be idempotent but it's rarely tested, and good luck if you want a way to rollback changes, or to avoid changes after the initial setup.
- ephemeral environments: systemd, docker containers, initramfs. these let you modify the system in arbitrary ways at runtime, but will eventually be destroyed and recreated with your changes discarded.
- immutable environments: docker images, nix. these prevent you from modifying the system at all. docker images work by sandboxing the environment inside the build tool (usually with cgroups), then storing the images read-only. nix works by sandboxing your whole environment (removing `/lib64/ld-linux.so` altogether; removing most directories in the root file system; replacing files in /etc with symlinks to /nix/store).
- automatic syncing: kubernetes[^cyber-etymology], terraform, package managers. these *compare* your current state to the desired state, and act upon it to sync the two.

all of these have downsides. the downsides of "not our problem" are fairly obvious: you don't get nice things. the downside of ephemeral environments is two-fold: you can easily make changes you forgot about, only for things to break when the environment is discarded; and you use a different language (usually shell) for modifying the environment at runtime than for modifying the configuration file. the downside of immutable environments is that experimentation becomes harder (and often slower). the downside of syncing is that if your state becomes too "weird" your engine can give up and be unable to resolve the conflicts.

and of course, for all these except "not our problem", you have to update the configuration files for your changes to take effect.
## state tracking

i want to propose a fifth alternative: state tracking. before i dive in to how this could work for IAC, consider a state tracking mechanism that's already common: version control systems. git automatically notices changes, and allows you to choose when to "commit" your changes to a persistent record. [jj] takes this a step further and automatically commits your changes each time it runs (and has various UI patterns to make editing old changes easy so auto-commits don't get in the way).

i know several people who track their whole home directory in a git repo. this gets them the best of both worlds: they can make changes freely, rollback to earlier states, and sync their state between machines. the main downside is that it can only track the home directory, not the whole system; and it only works for text files, not binaries. it also has very limited support for having multiple configs; you can have branches, but you're responsible for keeping them up-to-date. finally some state is sensitive and shouldn't be stored in plaintext or uploaded remotely (for example a password manager database).
